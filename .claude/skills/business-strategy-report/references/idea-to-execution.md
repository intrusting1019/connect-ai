# 아이디어 회의 → 실행계획 → 실행 플레이북

보고서(정리·검수)가 "과거 자료"를 다룬다면, 이 플레이북은 "앞으로 할 일"을 다룬다.
사용자와 **회의(코칭 대화)** 로 아이디어를 구체화하고, 회의록을 바탕으로 **실행계획**을
수립하며, Claude가 만들 수 있는 산출물은 **직접 실행**까지 한다.

세 단계는 연속이지만 독립 진입도 가능하다 — 사용자가 이미 구체화된 아이템을 들고 오면
바로 2단계(실행계획)부터, 계획이 이미 있으면 3단계(실행)부터 시작한다.

---

## 1단계. 아이디어 회의 (Idea Development Session)

### 회의 원칙
- **코치이지 강사가 아니다.** 지식 베이스를 강의하지 말고, 프레임워크를 *질문*으로 변환해
  사용자가 스스로 답을 찾게 하라. 사용자의 답이 5/5 권위 항목과 충돌할 때만 근거를 들어
  반박하라 (예: "모두를 위한 제품"이라 답하면 → 고딘의 최소 유효 시장으로 되물어라).
- **한 번에 한 묶음만 묻는다.** 선택지가 갈리는 지점은 AskUserQuestion(있으면)을 쓰고,
  열린 탐색은 일반 대화로 한다. 질문 폭탄 금지 — 스테이지당 핵심 2~4개.
- **모든 결정을 회의록에 기록한다.** `meeting-log.md`(또는 사용자가 지정한 위치)에
  스테이지별 결론·근거·보류 항목을 남긴다. 이 파일이 2단계의 입력이다.
- 사용자가 이미 답한 것을 다시 묻지 마라. 자료를 먼저 받았으면 그 안의 답을 채워 넣고
  빈칸만 물어라.

### 스테이지별 질문 은행 (프레임워크 → 질문 변환)

**S1. 씨앗 파악** — 아이디어의 기원과 동기
- 이 아이디어는 직접 겪은 문제에서 나왔나, 아니면 '떠올리려고' 만든 것인가? (그레이엄: 유기적 vs 지어낸)
- 당신에게는 놀이처럼 느껴지지만 남에게는 일처럼 보이는 강점이 무엇인가? (나발: 특정 지식)
- 5~20년을 해도 좋을 주제인가, 단기 수익용인가? (1인 기업의 장기 프로젝트 관점)

**S2. 문제·고객 검증** — Mom Test + JTBD
- 이 문제를 실제로 겪는 사람이 *마지막으로* 그 문제를 겪은 게 언제이고, 그때 어떻게 해결했나?
  (미래 가정 금지 — 과거의 구체적 사실만)
- 고객은 어떤 상황에서 무엇을 '고용'하려 하는가? 기능·사회·감정 중 어느 차원이 큰가? (JTBD)
- 형편없는 v1이라도 쓸 만큼 절실한 사람은 정확히 누구인가? (그레이엄)

**S3. 시장·차별화** — 틸 + 호르모지 + Playing to Win
- 매우 소수만 동의하는, 당신이 아는 중요한 진실은 무엇인가? (틸의 비밀)
- 시장 4지표 점검: 고통이 극심한가 / 구매력이 있는가 / 타겟팅이 쉬운가 / 성장 중인가? (호르모지)
- 어디서 싸우고(Where to Play) 어떻게 이길 것인가(How to Win)? 안 할 것은 무엇인가? (마틴·포터)

**S4. 가치 설계** — 가치 방정식 + ERRC + 포지셔닝
- 꿈의 결과를 키우고 시간·노력을 줄이는 방법은? (가치 방정식의 분자↑ 분모↓)
- 업계 관행 중 제거/감소/증가/창조할 요소는? (ERRC)
- 이 제품이 없다면 고객은 뭘 쓰나? 그 대안 대비 고유 속성과 증거는? (던포드 5요소)

**S5. 수렴** — 회의 종료 조건
- **승리 가설 한 줄**: "누구의 어떤 할 일을, 무엇으로, 왜 우리가 이기는 방식으로" 문장 완성.
- **가장 위험한 가정 Top 3** 도출 (마우리아: riskiest assumption first).
- 사용자에게 승리 가설·가정 목록 확인을 받은 뒤 2단계로 넘어간다.

한 세션에 다 끝낼 필요 없다 — 사용자가 지치면 회의록 저장 후 "다음 회의에서 S3부터"로 재개.

## 2단계. 실행계획 수립 (Execution Planning)

회의록의 승리 가설·가정을 계획으로 변환한다. 산출물은 `.docx`(build_report.js) 또는
Markdown — 사용자 선호를 따른다.

### 실행계획 문서 구조
```
# [아이템명] 실행계획
## 1. 승리 가설 (한 줄) + 근거가 된 회의 결정 요약
## 2. 린 캔버스 요약 (9블록 표)
## 3. 위험 가정 → 검증 실험 매핑 (아래 실험 메뉴에서 선택)
## 4. 90일 로드맵 (OKR 형식)
## 5. 주간 체크인 계획
```

### 검증 실험 메뉴 (가정 유형 → 실험)
| 가정 유형 | 실험 | 성공 기준 예시 |
|---|---|---|
| "이 문제가 진짜 고통이다" | Mom Test 인터뷰 5~10건 | 최근 3개월 내 해결 시도 경험 ≥ 절반 |
| "고객이 돈을 낸다" | 사전판매·예약금·LOI | 목표 전환율 사전 합의 (예: 방문자의 3%) |
| "제품이 가치를 준다" | MVP/컨시어지 테스트 | Sean Ellis 40% (못 쓰면 '매우 실망') |
| "채널이 작동한다" | Core Four 중 1개 소규모 테스트 | CAC < 목표 LTV의 1/3 |
| "지속 사용한다" | 2주 리텐션 관찰 | 재사용률 목표 사전 합의 |

실험엔 반드시 **사전 합의된 성공/실패 기준**을 붙인다 — 기준 없는 실험은 확증편향 수집이다.

### 90일 로드맵 (OKR 형식)
- 형식: "나는 [Objective]를 [KR 3~5개]로 측정하며 달성한다."
- 구간: **0~30일 검증**(가정 실험) → **31~60일 MVP/첫 제공** → **61~90일 첫 고객·매출**.
- 각 구간 끝에 **피벗/지속 게이트**: 실험 결과가 기준 미달이면 자동으로 회의(1단계 S3~S5)로
  복귀한다. 이것이 실패가 아니라 시스템이 작동하는 것임을 사용자에게 상기시켜라 (BML 루프).
- 되돌릴 수 있는 결정(Type 2)은 빠르게, 되돌릴 수 없는 결정(Type 1)만 신중히 (베조스).

## 3단계. 실행 (Execution Support)

계획에서 Claude가 직접 만들 수 있는 산출물은 만들어 주고, 사용자가 해야 할 일은
추적 가능한 형태로 관리한다.

### Claude가 직접 실행 가능한 것 (해당 실험/마일스톤에 맞춰 제작)
- Mom Test **인터뷰 스크립트** + 응답 기록 템플릿
- **랜딩페이지** 카피/HTML, 사전판매 페이지 문구
- **MVP 스펙** 문서, 상세페이지(웹툰형 구성 포함), 브랜드 네이밍 후보
- **콘텐츠 캘린더**(Building in Public용), SNS 게시물 초안
- 시장·경쟁사 **딥리서치** (본 스킬의 3회 검수·신뢰도 방식 그대로 적용)
- 실험 결과 **분석·판정 보고서** (기준 대비 통과/미달, 다음 액션)

### 태스크 관리
- 태스크 도구(TaskCreate 등)가 있으면 마일스톤·실험을 태스크로 등록하고 상태를 갱신한다.
- 없으면 `execution-checklist.md`를 만들어 체크박스로 관리하고, 저장소 프로젝트라면 커밋한다.

### 주간 체크인 (선택)
- 스케줄 도구(send_later, cron 등)가 있으면 사용자 동의를 받아 주간 체크인을 예약한다.
- 체크인 프로토콜: ① 지난주 실험/태스크 결과 확인 ② 기준 대비 판정 ③ 계획 갱신
  ④ 피벗/지속 판단 필요 시 회의 소집. 결과는 회의록에 누적한다.
- 진행이 없어도 질책하지 마라 — 장애물을 물어 계획을 현실에 맞게 수정하는 것이 체크인의 목적이다.

### 실행 단계의 마인드셋 가드레일 (지식 베이스에서)
- 첫 버전이 부끄럽지 않다면 너무 늦게 출시한 것이다 (호프먼) — 완벽주의로 지연되면 이 원칙을 들어라.
- 확장 안 되는 일을 하라 (그레이엄) — 초기엔 수작업 영업·수동 온보딩이 정상이다.
- 결과로 평가한다 (미스터비스트) — 체크인은 시간이 아니라 검증된 학습량을 센다.
